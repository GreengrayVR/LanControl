# LanControl

Клієнт-серверна програма C++20 для Windows 10/11 x64. Сервер має інтерфейс українською на Qt Widgets; клієнт складається з Windows-служби та фонового агента в сеансі кожного користувача.

Проєкт для Windows 10/11 x64, MSVC 2022, Qt 6.8.3. Спільний клієнт версії 2 зібрано статично: `deployment/single-file/LanClient.exe`. Для KABINET6-R1–KABINET6-R6 передається один і той самий EXE без DLL або сусіднього `client.json`. Сервер із чинним сертифікатом залишається багатофайловим у `deployment/server`. Стан перевірок наведено у `VALIDATION.md`.

## Запуск готової збірки

- Сервер: `deployment/server/LanServer.exe`. Запустіть подвійним клацанням або з кореня проєкту: `& .\deployment\server\LanServer.exe`.
- Спільний клієнт без DLL: `deployment/single-file/LanClient.exe`. Копіюйте на всі шість ПК лише цей файл.
- На серверний ПК скопіюйте весь каталог `deployment/server`. Його мережеве ім’я або DNS-псевдонім має бути `6kabinet`, доступний усім клієнтам. Дозвольте вхідний TCP 47666 для локальної мережі (сценарій `scripts/Enable-ServerFirewall.ps1` запускається адміністратором).
- На кожному клієнтському ПК запустіть скопійований `LanClient.exe` та підтвердьте UAC. Клієнт установиться як служба, сам визначить ім’я ПК та надалі запускатиметься автоматично. Налаштування вже вбудовано в EXE.
- Зберігайте `server-data` поруч із серверним EXE: там містяться налаштування та сертифікат. На клієнти передавайте лише статичний `LanClient.exe`.
- Потрібен оновлений `deployment/server/LanServer.exe`. Якщо сервер уже скопійовано на інший ПК, замініть там EXE та `server-data/computers.json` файлами з цього deployment, зберігши сертифікат і приватний ключ. Раніше встановлені персональні клієнти продовжують працювати.

## Статичний клієнт

Qt Core, Qt Network, плагін Schannel та MSVC Runtime скомпоновано в EXE. Для TLS клієнт використовує системний Schannel Windows. DLL не розпаковуються. Початкові endpoint, токен і pin сертифіката з `deployment/client/client.json` вбудовано через Qt Resources. Статична збірка перевіряє ім’я сервера, строк дії та SHA-256 pin сертифіката.

Інсталяція копіює лише власний EXE у `%ProgramFiles%\LanControl` та підкаталог версії; сусідні файли з робочого столу або флешки не копіюються. Службові JSON, журнал і черга команд зберігаються в `%ProgramData%\LanControl`. Для переходу з раніше встановленої DLL-збірки без залишкових DLL виконайте чисте перевстановлення за розділом 4.

Для повторення збірки потрібні вихідні коди Qt Base 6.8.3 у `.build-tools/qtsrc`. Використано [офіційний архів Qt](https://download.qt.io/archive/qt/6.8/6.8.3/submodules/qtbase-everywhere-src-6.8.3.tar.xz), SHA-256 `56001b905601bb9023d399f3ba780d7fa940f3e4861e496a7c490331f49e0b80`.

```powershell
.\scripts\Build-StaticQt.ps1 -SourceDirectory '.\.build-tools\qtsrc'
.\scripts\Build-SingleFileClient.ps1 -Version 2
```

Вихідний каталог статичного клієнта має бути новим. SDK Qt збирається один раз із параметрами `-static -static-runtime -no-openssl -schannel` ([параметри Qt 6.8.3](https://github.com/qt/qtbase/blob/v6.8.3/config_help.txt)). Зміна спільного токена або pin для нових інсталяцій потребує повторної збірки EXE з актуальним `client.json`. Старі `deployment/client` та `LanClient.zip` збережено як попередній варіант із DLL.

## Можливості

- Сервер `6kabinet`, TCP `47666`, TLS 1.2 або новіший.
- Клієнт установлює постійне з’єднання, надсилає heartbeat кожні 20 секунд, повторює підключення кожні 20 секунд, якщо сервер недоступний.
- Служба автоматично запускається під LocalSystem під час завантаження Windows, до входу користувача. Агенти запускаються для всіх користувачів через HKLM Run; служба також перевіряє активні сеанси кожні 20 секунд.
- Клієнт не створює вікон, кнопок на панелі завдань або значка в треї. Браузер відкривається звичайним видимим вікном у сеансі користувача.
- Сервер читає мережеві імена ПК з `server-data/computers.json`. Зеленим показує підключені ПК, червоним — відключені. Після аварійної втрати зв’язку статус змінюється через максимум приблизно 65–66 секунд; коректне відключення видно одразу.
- Надсилання URL всім підключеним або вибраним ПК. Вибір кількох рядків: Ctrl/Shift. Дозволені лише HTTP/HTTPS, без облікових даних у URL.
- Натискання X ховає сервер у трей; повне завершення — правою кнопкою по значку → «Вийти повністю». Якщо трей недоступний, X завершує застосунок.
- Перевірка оновлень одразу після підключення й кожні 10 хвилин. Автоматичне завантаження, SHA-256, перемикання версії, перезапуск служби й агентів, відновлення попередньої версії після помилки старту.

Служби ізольовані від користувацького робочого столу, тому браузер відкриває агент під звичайним обліковим записом. Цю архітектуру описує [Microsoft: Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services). Qt-залежності збирає [windeployqt](https://doc.qt.io/qt-6/windows-deployment.html).

## 1. Збирання

На ПК розробника потрібні Visual Studio 2022 / Build Tools з «Desktop development with C++» і Windows SDK, CMake 3.24+, Qt 6.8+ **MSVC 2022 x64** з Core, Network, Widgets, Test, а також OpenSSL 3 x64. Команди нижче виконуйте з кореня проєкту в PowerShell. Шляхи Qt/OpenSSL замініть власними.

```powershell
.\scripts\Build.ps1 -QtRoot 'C:\Qt\6.8.3\msvc2022_64' -OpenSslBin 'C:\OpenSSL-Win64\bin' -Version 1
```

Сценарій компілює Release, запускає `ctest` і створює `dist-v1/LanClient` та `dist-v1/LanServer` з DLL, Qt-плагінами й OpenSSL. Копіюйте **весь каталог** відповідного застосунку. На кінцевих ПК Qt/Visual Studio встановлювати не потрібно; пакет містить залежності, зібрані windeployqt. Якщо Microsoft Visual C++ Runtime відсутній і конкретний Qt kit поширює його окремим інсталятором, встановіть офіційний VC++ Redistributable x64, який видав windeployqt.

Ручні команди збирання:

```powershell
cmake -S . -B build -G 'Visual Studio 17 2022' -A x64 -DCMAKE_PREFIX_PATH='C:\Qt\6.8.3\msvc2022_64' -DLANCONTROL_VERSION_CODE=1 -DBUILD_TESTING=ON
cmake --build build --config Release --parallel
# Qt bin має бути в PATH під час запуску тестів:
$env:PATH = 'C:\Qt\6.8.3\msvc2022_64\bin;' + $env:PATH
ctest --test-dir build -C Release --output-on-failure
```

## 2. Сертифікат, список ПК та спільний клієнт

У `config/computers.txt` запишіть реальні мережеві імена: один ПК у рядку. Ім’я можна перевірити командою `hostname`. Імена нечутливі до регістру; приклад:

```text
kabinet6-r1
kabinet6-r2
kabinet6-r3
kabinet6-r4
kabinet6-r5
kabinet6-r6
```

```powershell
.\scripts\New-Deployment.ps1 -BundleDirectory '.\dist-v1' -OutputDirectory '.\deployment' -OpenSslExe 'C:\OpenSSL-Win64\bin\openssl.exe'
```

Результат:

```text
deployment/
  server/LanServer.exe, Qt DLL та плагіни
  server/server-data/computers.json     список ПК, спільний токен та токени сумісності
  server/server-data/server.crt         публічний сертифікат 6kabinet
  server/server-data/server.key         приватний ключ, лише на сервері
  server/server-data/updates/           файли наступного оновлення
  client/LanClient.exe, client.json, DLL та плагіни — однакові для всіх ПК
```

Сценарій генерує спільний випадковий 256-бітний токен і фіксує SHA-256 сертифіката сервера в `client/client.json`. Усі ПК використовують однаковий пакет, а сервер розрізняє їх за мережевими іменами. Підключатися можуть лише імена зі списку `computers.json`. Каталог deployment обмежений поточним користувачем, адміністраторами та SYSTEM. Приватний ключ і серверна конфігурація залишаються на сервері.

У робочому серверному файлі список має формат:

```json
{"sharedClientToken":"64 шістнадцяткові символи, створені сценарієм","computers":[{"name":"KABINET6-R1","token":"індивідуальний токен для сумісності з попередніми клієнтами"}]}
```

Щоб додати ПК, внесіть його ім’я та новий випадковий індивідуальний токен у цей файл і перезапустіть сервер. На новий ПК копіюється той самий спільний клієнт. Не генеруйте весь deployment заново для звичайного оновлення: новий сертифікат перестане відповідати pin установлених клієнтів.

Для переходу з персональних пакетів на спільний без заміни чинного сертифіката:

```powershell
.\scripts\New-SharedClient.ps1 -ClientBundleDirectory '.\dist-shared\LanClient' -ServerDataDirectory '.\deployment\server\server-data' -OutputDirectory '.\deployment\client'
```

Цей перехід уже виконано для поточного deployment. Сценарій вимагає нового вихідного каталогу, зберігає індивідуальні токени й повторно використовує наявний спільний токен. Початкова серверна конфігурація збережена в `computers.json.before-shared`. Старі персональні пакети в `deployment/clients` залишено як резервні; для нових установлень використовуйте спільну папку `deployment/client`.

## 3. Запуск сервера

Скопіюйте каталог `deployment/server` на комп’ютер із мережевим ім’ям **6kabinet** у каталог, доступний для запису лише адміністратору/оператору сервера. Ім’я `6kabinet` має визначатися на всіх клієнтах через DNS або локальне розв’язання імен. Для іншого фізичного імені створіть DNS-псевдонім `6kabinet`.

Від адміністратора один раз дозвольте вхідні з’єднання локальної підмережі:

```powershell
.\scripts\Enable-ServerFirewall.ps1
```

Правило застосовується до профілів Private/Domain. Потім запустіть `LanServer.exe`. Типовий шлях даних — `server-data` поруч із EXE. Інший каталог передається єдиним аргументом:

```powershell
.\LanServer.exe 'D:\LanControlData'
```

Сервер працює, поки оператор увійшов у Windows і застосунок запущений. Автозапуск сервера за бажанням налаштовується окремо; закриття в трей продовжує обслуговувати клієнтів.

## 4. Установлення клієнта

На кожному ПК запустіть той самий статичний `deployment/single-file/LanClient.exe`. Перший запуск виконує `--install` і запитує стандартне підвищення прав UAC. Реєстрація Windows-служби та запис у HKLM потребують адміністратора; обійти цю вимогу Windows неможливо.

```powershell
.\LanClient.exe --install
```

Інсталятор копіює пакет у `%ProgramFiles%\LanControl`, створює автоматичну службу `LanControlClient`, додає агент у HKLM Run, записує конфігурацію в `%ProgramData%\LanControl` та запускає службу. Каталоги захищені ACL: звичайні користувачі мають читання/виконання, SYSTEM і адміністратори — запис. Запуск служби та агента надалі не показує UAC.

На вже встановленому ПК повторно запускати EXE без аргументів не потрібно. Для повторної інсталяції спочатку видаліть службу й залишкові каталоги. Інсталятор навмисно не використовує вже наявні каталоги, щоб служба SYSTEM не запускала підкладені файли. Якщо встановлення перервалося, перевірте стан служби та приберіть залишки від адміністратора перед повтором.

Якщо ніхто не увійшов у Windows, ПК залишається підключеним до сервера, але браузер немає де показати. Команда зберігається 60 секунд; агент може виконати її після входу протягом цього часу. У кожному активному користувацькому сеансі працює один агент. Браузер відкривається від імені цього користувача. На ПК має бути налаштований типовий браузер.

Команди потрапляють у захищену чергу `commands/*.json`, агент читає її раз на секунду. Максимум — 256 одночасно чинних команд. Дублікати відсікаються за UUID; стан зберігається в HKCU. Позначка `accepted by service` у серверному журналі означає прийняття службою, а не підтвердження завантаження вебсторінки браузером.

## 5. Автоматичне оновлення

Оновлюються код служби й агента в `LanClient.exe`. Для статичного клієнта наступні версії також збирайте через `Build-SingleFileClient.ps1` із більшим `Version`. Для старих DLL-збірок використовуйте той самий Qt kit, MSVC та сумісний набір DLL/OpenSSL: updater переносить чинний runtime до каталогу нової версії. Початковий EXE залишається стабільним launcher/updater; оновлення його власного алгоритму потребує повного розгортання.

1. Збільште цілочисельний `Version`: 1 → 2 → 3. Значення має збігатися в CMake та маніфесті.
2. Зберіть новий клієнт:

```powershell
.\scripts\Build-SingleFileClient.ps1 -Version 3 -OutputDirectory '.\dist-client-v3'
```

3. Завершіть сервер через трей, опублікуйте файл і запустіть сервер знову:

```powershell
.\scripts\Publish-Update.ps1 -ClientExe '.\dist-client-v3\LanClient.exe' -Version 3 -ServerDataDirectory 'D:\LanControl\server-data'
```

Клієнти перепідключаться протягом 20 секунд та перевірять оновлення. Без перезапуску перевірка виконується кожні 10 хвилин. Сервер передає файл блоками по 48 КіБ у вже автентифікованому TLS-з’єднанні; вхідні порти на клієнтах не потрібні.

Клієнт перевіряє новішу версію, розмір до 128 МіБ та SHA-256. Окремий updater із захищеного каталогу повторно перевіряє файл, копіює runtime у `versions/2`, зупиняє службу, змінює її шлях, атомарно змінює `current.json` і запускає нову версію. Після 5 секунд роботи служби оновлення вважається успішним. Агенти помічають новий шлях і перезапускаються. Старі версії залишаються на диску для відновлення; їх очищення адміністратор виконує окремо після перевірки роботи.

Якщо нова служба не запускається, updater повертає шлях і `current.json` до попередньої версії. Невдала версія записується в `failed-update.json` і автоматично вдруге не встановлюється. Виправлений пакет потрібно публікувати з **новим вищим номером**. Втрата мережі під час завантаження залишає чинну службу на місці; завантаження почнеться заново після підключення.

Автовідкат перевіряє запуск процесу та служби, а не всі функції нової версії. Раптове вимкнення живлення саме між зміною шляху служби й `current.json`, несправність диска або помилки пізніше ніж через 5 секунд можуть вимагати ручного відновлення. Для цього від адміністратора зупиніть службу, встановіть у `current.json` попередній номер, поверніть `binPath` через `sc.exe config LanControlClient binPath= '"C:\Program Files\LanControl\versions\1\LanClient.exe" --service'` і запустіть службу. Шлях Program Files перевірте для своєї системи.

Оновлення автентифіковане pin сертифіката TLS; SHA-256 підтверджує цілісність. Окремого офлайнового цифрового підпису EXE/маніфесту тут немає. Компрометація приватного ключа сервера або його облікового запису дозволяє розповсюдити код клієнтам, тому ключ і каталог updates повинні бути доступні лише довіреному адміністратору. Самопідписаний сертифікат чинний 5 років; pin і строк чинності перевіряються. Заміна сертифіката потребує контрольованого оновлення `certificateSha256` на клієнтах.

## 6. Діагностика й видалення

```powershell
Get-Service LanControlClient
Resolve-DnsName 6kabinet
Test-NetConnection 6kabinet -Port 47666
Get-Content "$env:ProgramData\LanControl\client.log" -Tail 40
```

Журнал обмежено приблизно 2 МіБ плюс один `.old`. URL і токени в нього не записуються. У `HKCU\Software\LanControl\Agent` значення `lastBrowserLaunch` містить `ok`/`failed` після спроби відкриття браузера. Синхронізуйте годинники ПК: строк дії команд і сертифіката перевіряється за системним часом.

```powershell
& "$env:ProgramFiles\LanControl\LanClient.exe" --uninstall
```

Потрібні права адміністратора. Видаляються служба й HKLM Run, агенти завершуються протягом секунди. Після цього закрийте інсталятор і видаліть **лише перевірені каталоги** `%ProgramFiles%\LanControl` та `%ProgramData%\LanControl` вручну. Дані залишаються для діагностики; автоматичного рекурсивного видалення з привілейованого процесу немає.

## 7. Перевірка перед розгортанням

`protocol_tests` перевіряє дозволені/заборонені URL, фрагментацію й об’єднання TCP-повідомлень, пошкоджені та завеликі кадри, SHA-256, заборону старих/некоректних версій і атомарний JSON. Ці тести запускає Build.ps1 після компіляції. Служби, UAC, TLS та браузер слід перевірити на двох тестових Windows-ПК за `tests/ACCEPTANCE.md`.
